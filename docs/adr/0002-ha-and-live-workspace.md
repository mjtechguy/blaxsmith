# ADR 0002: optional HA profile and durable live workspace

**Status:** direction accepted; specific Redis distribution and production versions require compatibility proof. **Date:** 2026-09-23.

Blaxsmith needs to run on one k3s node and also offer a supported HA production profile. Both use the same application, database schema, AX connector contract, and TanStack workspace. The single-node install has a backup/restore procedure but cannot claim node-level HA. The enterprise profile must meet the plan's stated RPO ≤15 minutes and RTO ≤4 hours **to usable authorized service** under a published failure model. Human review remains the final engineering gate regardless of deployment topology.

## Deployment decision

| Concern | Decision and reason | Proof still required |
|---|---|---|
| Product database | Use CloudNativePG for the in-cluster HA PostgreSQL profile; permit a managed PostgreSQL endpoint satisfying the same TLS, backup, failover, and restore contract. PostgreSQL stays authoritative for product workflow, identity, grants, events, and audit. | Pin operator/PostgreSQL versions and storage class; spread instances across failure domains; choose synchronous/failover-quorum policy from measured write durability versus availability; failover and connection-recovery test. [CNPG documents that asynchronous failover can lose data and synchronous mode alone does not guarantee promotion of the most advanced replica.](https://cloudnative-pg.io/docs/1.28/failover/) |
| Database backup | Use the [Barman Cloud CNPG-I plugin](https://cloudnative-pg.io/plugin-barman-cloud/docs/concepts/) for continuous WAL archiving and scheduled physical base backups to an independent object store. This is the current plugin path, not a separate Barman server. | Pin a mutually supported operator/plugin pair; provide object-store identity, TLS, encryption, retention, monitoring, and restore credentials; prove a [PITR restore into a new Cluster](https://cloudnative-pg.io/plugin-barman-cloud/docs/concepts/#recovery-of-a-postgres-cluster), not merely a successful backup Job. Plugin prerequisites and operational compatibility are documented [upstream](https://cloudnative-pg.io/plugin-barman-cloud/docs/intro/). |
| AX Redis | Treat Redis as AX execution-state storage, not a disposable frontend cache. The inspected AX manifests deploy a single Redis pod without a PVC; AX server/controller use one-address `redis.NewClient` with password support but no Sentinel discovery or Redis TLS configuration. Do not publish an HA claim by replacing its Deployment with a chart alone. | Evaluate a maintained Helm chart or managed service, including artifact/image availability and support terms. A replication/Sentinel chart is a plausible candidate—the [Bitnami chart](https://github.com/bitnami/charts/blob/main/bitnami/redis/README.md) documents that topology—but select it only after AX can authenticate, use protected transport, follow promotion, reconnect, and reconcile uncertain tasks. Pin chart/images and test state persistence/restore. Redis Cluster sharding is a separate compatibility question; no v1 need has been shown. |
| Other durable inputs | Keep object artifacts, AX snapshots/state, signing/encryption keys, and recovery operator credentials in the coordinated recovery plan. An archived PostgreSQL WAL stream cannot recreate these. | Restore every required byte and key from independent custody, then enter restricted recovery, invalidate old sessions/leases/owners, and reauthorize authority lost within the RPO window. Test interrupted publication and disconnected execution clusters. |
| Application/connector | Use multiple replicas with durable ownership/fencing, readiness, resource requests, failure-domain placement, and disruption budgets when qualified. The app chart presently has one replica, no ingress, and no connector; those are implementation tasks. | Stop all old writers during scheduled schema migration; rolling app/database upgrades are deferred. Demonstrate failed-node and replica replacement, event delivery, and no duplicate dispatch/publication. |

Keep CNPG, Barman plugin/object-store configuration, and AX Redis as separately operated, pinned dependencies. The Blaxsmith Helm package consumes verified endpoints and precreated Secret/CA references. This avoids coupling an application rollback to an unrelated database/chart lifecycle. A one-node install may share the same contract and manifests, but reports only its tested backup/restart behavior. Do not infer zonal or cluster survival from three pods placed on one node or one storage failure domain.

The Barman plugin's [retention policy](https://cloudnative-pg.io/plugin-barman-cloud/docs/retention/) defines a recovery window, which must be chosen with product artifact/audit retention and backup storage policy. Monitor last successful base backup, WAL archive lag/failures, object-store availability, replication lag, volume capacity, failover time, and restore rehearsal age. Backups are only evidence of recoverability when a restore and product authority reconciliation pass.

## Browser event decision

Use one same-origin SSE connection for the active authorized workspace scope. The server writes `text/event-stream` events only after the corresponding PostgreSQL transition and durable event commit. Each event has a stable scoped ID, resource kind/ID, and revision; it carries no secrets, raw agent output, or permission inferred from an untrusted tool. A snapshot query returns current authorized state and its cursor; the stream resumes after that cursor, and the browser's [`Last-Event-ID`](https://html.spec.whatwg.org/dev/server-sent-events.html#the-last-event-id-header) supports reconnect. If the cursor has expired or its scope is invalid, return a reset condition and refetch the snapshot. Duplicates must be harmless. Cross-replica fan-out can use notifications as a wake-up hint, but replay comes from durable events, so no sticky load-balancer session is needed.

Authenticate the same-origin cookie-backed stream on connect and repeatedly against current membership and resource scope. Revoke/close immediately on known access loss and clear the matching TanStack Query cache; revalidate during idle periods so a long-lived connection cannot outlast policy. A browser auth expiry follows the normal refresh path before stream reattachment. Do not send access tokens in URLs, local storage, or SSE payloads. Bound stream buffers and send lightweight heartbeats; reconnect a slow client from its durable cursor rather than retaining unbounded memory. Test response buffering and idle timeouts at the chosen ingress/proxy. SSE signals a targeted TanStack Query invalidation/refetch; the typed Connect API remains the authoritative snapshot and mutation path. TanStack's [server-side table guidance](https://tanstack.com/table/latest/docs/guide/client-side-vs-server-side) also requires server filtering/sorting when pagination is server-owned, so live hints must never cause a page-local sort/search to masquerade as whole-dataset state.

The visual contract is enforced from the start: a single `frontend/src/styles.css` entry, central semantic tokens and typography, shared chrome/PageShell/Form, the canonical TanStack Table for collection pages, routed configuration, and confirmation-only modals. Review or lint rejects alternate global stylesheets, custom collection tables, ad hoc color palettes, browser dialogs, and drawers. Existing [frontend adoption inventory](../frontend-adoption.md) records the AGPL source/licensing gate; this ADR does not authorize copying Astronomer source.

The tools, project, and run collection routes now render through one shared DataTable. The global stylesheet still contains some preview-era hard-coded colors; P1-14 replaces these with the agreed semantic tokens. P1-17 extends the shared table with the required server-owned search/sort/pagination and enterprise controls; calling `useTable` in each page alone does not complete that contract.

## Delivery and acceptance

| Phase | Task and observable gate |
|---|---|
| 0 (`P0-13`) | Record tested CNPG/Barman compatibility candidates, AX Redis protocol/client gaps, chart/image/support choice, failure model, backup inventory, SSE cursor/retention/ingress contract, and UI/event load thresholds. |
| 1 (`P1-25`, `P1-14/17/19`) | Ship authenticated SSE replay over durable events and one scoped TanStack Query consumer; provide a built-app browser test for reconnect/revocation/scope loss. Enforce global CSS and shared table/page/form components in review and regression checks. |
| 2 (`P2-10`) | Exercise bursty concurrent run updates, filtering/selection/editing during refresh, disconnected browsers, and authorization changes at realistic task counts. Measure request rate, event lag, DOM/memory, and interaction latency. |
| 3 (`P3-06/08/11`) | Install pinned optional HA profile; inject pod/node/declared-zone failures, restore a fresh CNPG cluster to a chosen point, and recover artifacts/keys/AX state. Prove Redis promotion/reconciliation and restricted authority, publish RPO/RTO and 100-worker results plus unsupported topologies. |

No Redis chart, CNPG version, Barman schedule, synchronous-mode setting, or ingress timeout is a production default until these gates have measured evidence. This decision records the supported direction and the exact work needed to make the option real.
